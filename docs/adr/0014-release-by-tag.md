# Releases are cut by pushing a `v*` tag

`NgheTruyen.exe` has been buildable by hand since ADR-0012, with the PyInstaller
command in `app/README.md`. That is enough for the machine it was built on and
nothing else: the exe exists only there, and nothing ties it to the commit it
came from.

`.github/workflows/release.yml` now builds it on a `windows-latest` runner and
attaches it to a GitHub Release:

```bash
git tag v1.0.0
git push origin v1.0.0
```

The tag *is* the release: the workflow checks out that tag, runs the tests,
runs the build `app/README.md` documents (`PyInstaller NgheTruyen.spec`), and
uploads `dist/NgheTruyen.exe` as the release's only asset. Notes are GitHub's
generated changelog with `.github/release-notes.md` prepended -- the asset's own
description (what the exe is, that the Sidecar is still needed, that it is
unsigned) is the same for every version, so it lives in a file rather than in
the workflow, and the per-version part is the commits.

Running the workflow by hand (`workflow_dispatch`) skips the release and keeps
the exe as a workflow artifact instead. That is how to try a change to this
pipeline without publishing a version, and it is the reason the release step is
conditional rather than the workflow being tag-only.

Five things are deliberate:

- **The tests gate the release.** They run before the build, so a tag that
  fails them publishes nothing. They are fast (under a second locally) and need
  no Sidecar, no audio device and no network -- everything external is patched.
- **The build is the spec, not a flag list.** `app/NgheTruyen.spec` is committed
  and holds what goes into the exe -- `web/`, `assets/`, `console=False`, and
  `icon=assets/nghetruyen.ico` -- so a release and a local build cannot drift.
  Running PyInstaller *on the spec* (rather than with flags) is also what keeps
  it from being regenerated by a build; it used to be a gitignored artifact of
  `--add-data`/`--icon` flags, and `.gitignore` no longer excludes it.
- **Only the exe is attached.** The Sidecar stays a separate checkout with its
  own venv and model (ADR-0008, ADR-0012), so a release is one file. The release
  notes say so, because an exe downloaded on its own will not play anything
  until `sidecar/` exists beside it.
- **`gh` rather than a release action.** The runner has the GitHub CLI, so the
  release step needs no third-party action to trust or pin; `--verify-tag`
  stops it inventing a tag on the default branch, and `--notes-file` plus
  `--generate-notes` is what prepends the asset description to the changelog.
- **Nothing is pinned.** `app/requirements.txt` has no versions, so a release
  bundles whatever `pip install` resolves that day, and a new NiceGUI could
  break the bundle without a commit saying so. Pinning is its own decision -- it
  changes the local bootstrap flow (it reinstalls whenever the hash changes) and
  is not made here; until then, a release built from an old tag is not
  necessarily reproducible.

What the pipeline does not do: sign the exe (SmartScreen warns on first run, as
the notes say), produce an installer (ADR-0012's portability is the point), or
exercise the built exe -- a windowed build wants a desktop session, so the first
launch on a real machine is still the smoke test, and the release notes name
`sidecar.log` for when it goes wrong.
